# R6 — 审计尾读冷启动窗口化（2026-09-05）

> 对比链：R0→…→R5→本轮 `R6-audit-cold`。JSON：
> `benchmark/results/R6-audit-cold-go.json`（5×5 轮中位）。基线为优化前
> 同基准实测（BenchmarkPerfAuditCold100k，10 万行 ~16MB 夹具，每轮显式
> 重置增量缓存测真实冷路径）。

## 背景

`readAuditTail`（R0 之前引入的增量缓存）的**冷启动**路径：缓存失效
（面板重启、审计清理、扩容重建）后偏移归零，从 0 读到文件尾全量解析，
而最终只保留尾部 ≤500 条。审计日志长期运行到数十 MB 时，事件页首开/
每次缓存重建都要付一次全量解析（面板概览自己都有「>200MB 拖慢事件页」
的提示——本优化正是把这个提示的成因消掉）。

## 基线（优化前）

| 指标 | 值 |
| --- | ---: |
| ns/op（中位） | **283 459 859（~283ms）** |
| B/op | 143 907 489 |
| allocs/op | 1 300 036 |

## 改动（server/dashboard/parse.go）

- 冷读窗口 `auditColdWindow = 1MB`：偏移归零且文件超窗时跳到
  `size-1MB` 只解析尾部。窗口取值依据：audit.c 行缓冲上界 512B
  （第 6 轮审计已把截断行为定为有界降级行，行长有硬上界），
  1MB 恒容纳 ≥2000 行 = API 上限 500 条的 4 倍；
- 单一 bufio reader 丢弃窗口起点残行（防预读丢字节），残行字节按
  ReadBytes 返回长度计入偏移记账；
- **精确性兜底**：窗口内凑不足请求量（病态超长行的理论情形）→ 作废
  窗口路径从零全量重读，结果与原实现逐条一致；
- 增量语义不变：c.off 仍指最后一个完整行之后，末尾半行不消费留待
  下次补齐、截断/轮转检测、nMax 扩容重建均保持原行为。

## 优化后（中位）

| 指标 | 基线 | R6 | 提升 |
| --- | ---: | ---: | ---: |
| ns/op | 283 459 859 | **17 360 983** | **16.3×** |
| B/op | 143 907 489 | 9 176 719 | 15.7× |
| allocs/op | 1 300 036 | 83 707 | 15.5× |

（成本与文件大小解耦：任意大的审计日志，冷读恒定 ~1MB 解析。）

## 红线验证

- `TestR6AuditTailWindow`：2 万行 + 尾部 400B 超长行夹具，窗口读结果
  与「全量解析取尾」逐条比对（时间戳+用户名字段），末条一致性显式断言；
- 全量 `go test` 通过（R3/R5/掩码回归无影响）；`go vet` 干净。

## 用户体感

事件页首开、面板重启后首次轮询、审计清理后的重建，从「与日志体积
成正比的卡顿」变为恒定 ~17ms；配合 R5（oplog）后，面板所有日志类
读取（热/冷）均与文件大小解耦。
