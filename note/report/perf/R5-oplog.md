# R5 — dashboard 操作日志读尾缓存（2026-09-05）

> 对比链：R0→R1→R2→R3→R4→本轮 `R5-oplog`。JSON：
> `benchmark/results/R5-oplog-go.json`（5 轮中位数；基线为优化前同一
> 基准实测，5000 条日志夹具 ~750KB，超过读尾 256KB 窗口）。

## 背景

R3 覆盖了 metrics/access/tofu 三处轮询重读，遗漏操作日志：
`readOpLogTail` 每次调用重扫 256KB 窗口并逐行 `json.Unmarshal`，消费方
是 **`/api/oplog` 轮询**与**登录「上次登录回顾」（每次登录 500 条扫描）**。

## 基线（优化前实测）

| 指标 | 值 |
| --- | ---: |
| ns/op | **3 695 249 ~ 3 958 930（中位 ~3.75ms）** |
| B/op | 1 686 203 |
| allocs/op | **22 564** |

## 改动（server/dashboard/oplog.go）

- `opLogCache`：键 = 当前文件与 `.bak` 双文件的 `(size, mtime_ns)`，
  容量 1000 条（与 API 上限一致）；
- 命中（n ≤ 容量且键未变）→ 2 次 stat + 切片拷贝；未命中 → 原直读路径
  （原逻辑原样保留为 `readOpLogTailDirect`）按容量 1000 取数后存档；
- n > 1000 直读（超出 API 允许范围，语义兜底）；条目不足时仍跨 `.bak`
  补齐，轮转边界语义不变；
- 返回一律副本（命中与未命中两条路径都拷贝）；
- 失效：`logOp` 追加 / 8MB 单代轮转 / 文件删除都改变 stat 键。

## 优化后（中位）

| 指标 | 基线 | R5 | 提升 |
| --- | ---: | ---: | ---: |
| ns/op | 3 744 820 | **28 463** | **~132×** |
| B/op | 1 686 203 | 17 286 | ~98× |
| allocs/op | 22 564 | 121 | ~186× |

## 红线验证

- `TestR5OpLogCacheInvalidation`：冷读/暖读一致 → `logOp` 真实写路径
  追加后立即可见 → 文件删除回退空；
- 全量 `go test` 通过（QR/R3 掩码/审计回归不受影响）；`go vet` 干净；
- 语义等价论证：直读按容量取足再裁尾，尾部 n 条与逐级读取结果相同
  （含「当前文件不足时补 .bak」边界）。

## 用户体感

- 登录响应不再吃一次 ~3.7ms 的全窗口扫描（500 条）；
- 操作日志页轮询（10s 级）的每次后端成本从毫秒级降到微秒级；
- 长跑增长友好：日志涨到 8MB 触发轮转前，读成本恒定（窗口封顶）。
